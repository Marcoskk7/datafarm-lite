# datafarm-lite: instructions for any coding agent

This is a fork of DataFarm (`DAGroup-PKU/PyRUA-Lean`, branch `DataFarm`, commit `d788388`, MIT).
It takes a YAML request, builds the scene in simulation and produces action-labelled episodes.
It takes no real calibration episode and renders no video-model observations: its output is
**not real-ready data** and must never be reported as such. See "Fork scope" below.

Your job is to turn a data request into independently verified, action-labelled synthetic
episodes in simulation. You are the general task compiler, not a selector of
prebuilt task adapters. Read prompts/instructions/agent-start.md and follow .agents/skills/pipeline-orchestrate/SKILL.md.
The absence of a matching task name, adapter, task brief or video prompt is expected:
observe, derive, implement, test and generate them. Never ask the user to write these for you.

## Authority and instruction loading

1. Read prompts/instructions/instruction-layers.md, authority-and-scope.md and mode-and-style-contract.md.
2. Read prompts/roles/orchestrator.md and the stage skills listed in configs/agent-instructions.json.
3. Use `python tools/pipeline_agent.py context --role orchestrator --output /tmp/datafarm-context`
   for a fully expanded, hash-recorded context. This explicitly loads instructions even when your
   host does not discover .agents/skills. Follow its file routing.
4. The user's current instructions take priority. Preserve valid in-scope authorization. Ask only for
   genuinely missing intent, inaccessible inputs/resources or permissions, after inspecting what
   is available. Infer and validate technical choices yourself. Unknown OOD versus sim2real intent
   must be resolved before rendering; it does not block grounding or local implementation.

## Fork scope

Kept from upstream: the task-expert harness (`xh` broker, OS sandbox, AST audit, round resume,
budgets), the frozen judge and hidden holdout, the run ledger, admission checks, the agent

Replaced by this fork: grounding (the input is the request YAML, not a real episode), the

`sim-grounding` and `build-observed-object`.

## Invariants

  camera fit, prompts, run configs and reports are second-layer OUTPUTS. Outputs of other tasks are
  not prerequisites, global rules or authorization for a new task.
- Use full episodes as the unit; splitting for video transport does not change action semantics.
- Rendering reproduces the simulated episode: cameras, materials and lights come from the render
  spec, and the recorded state trace is the only source of motion and contact. There is no
  real-world image conditioning in this fork; do not claim photographic realism or real-ready data.
- The producer must not self-certify success. Separate task-contract review, expert development,

  Use the deployment's scheduler and permission scope, not a machine or allowance copied from elsewhere.
- Use source-bound admission for datasets. Training is downstream and only when requested; declare
  state/action mode explicitly and verify deployment compatibility.
- Runtime reads only explicit instructions and scoped experience. Keep new task output under the run

- Preserve user changes. New general behavior belongs in core/skills with meaningful tests;
  new per-task logic belongs in generated task outputs. Do not build a frozen task registry.

Engineering: install with `pip install -e '.[dev,workflow]'`, then `make test lint audit`.

proof of physical or visual quality. The source checkout is the deliverable.

# General capability and task outputs

DataFarm takes a robot task, scene and real episode it has not seen before, and the agent autonomously
completes understanding, scene adaptation, expert development, verification, batch collection and photographic data
production. The input episode is a complete real-robot record: a single video, or multi-camera videos with
actions/states, camera parameters and device information. The output is a dataset that keeps its correspondence to the
simulated actions, with provenance and independent review records. Training is an optional downstream step.

## First layer: the shared capability

- `.agents/skills/`: how to observe, propose verifiable hypotheses, generate implementations, trial-run, diagnose,
  correct, scale the batch and resume.
- `prompts/roles/`: the responsibilities of each role.
- `prompts/render/`: the real-reference, action-fidelity and style requirements that a task cannot override.
- `prompts/instructions/`: authority, evidence and the handoffs between stages.
- `src/datafarm/instructions.py`, `src/datafarm/task/contract.py` and `src/datafarm/render/delivery.py`: load these instructions explicitly and verify task outputs.
- The expert harness, run ledger, batch supervisor, providers and admission: execution tools.

A new task with no adapter in the repository is not a capability gap: the agent generates a new adapter, brief, judge
and initial-state sampler from the new task. Judge a missing general capability by whether the agent knows how to
generate it, can call tools to verify it, and will diagnose and recover from a failure.

## Second layer: the products of one task

| Output | Who generates it, based on what | Purpose |
|---|---|---|
| grounding.json / grounding.md | The orchestrator observes the complete real episode, reads device/calibration evidence and fits | Geometry, cameras, objects, actions, the identifiable range and uncertainty |
| task.json / requirements.md | The task designer, from the observations and the user's goal | Success relations, complete action phases, randomization axes, physical and collection criteria |
| scene / init / expert / adapter.json | The agent, using the simulator API and general interfaces | Randomized initial states, observation-to-action control, the rollout command for the broker |
| judge / verifier spec / brief | Independent contract-review and verification roles, frozen afterwards | Success criteria and negative controls; the expert author cannot edit the judge |
| render-overlay.json / render prompt | The orchestrator, from the task, cameras and real references | The objects, events, views and continuity of this task; they cannot cancel the general rules |
| batch configs / dataset spec / receipts | The orchestrator and an independent verifier | Batch scaling, review, admission, data export and reproduction |

These files go in `runs/<run-id>/task/` or the workspace the user names, with the manifest and hashes registered. The
templates under `configs/` are starting points, not task results. Never load the thresholds, mode authorizations, model
choices or prompts of an unrelated task automatically. File extensions do not tell the layers apart.
`tools/audit_instruction_layers.py` classifies files by layer; the loading manifest is `configs/agent-instructions.json`.

## Changing the layers

Requirements specific to a new task go only in the second layer. Change the first layer only for a verifiable defect
that spans tasks, and update the skill, prompt, verifier and tests together. Success on one task does not authorize OOD
on another, and a numerical threshold of one task is not a general truth. Keep earlier outputs and failure evidence, and
never manufacture compliance with a new policy by rewriting existing certificates.

# Authority, scope and authorization

The same task uses one explicit goal from the request, prompt and payload through to review.

**Conflicts.** Within the host platform's higher-level instructions, resolve conflicts in this order: the user's current
explicit request; still-valid user decisions with a matching scope; reproducible raw evidence; summaries; progress notes
and drafts. A later date does not turn an unapproved inference into a user decision. Raw evidence can overturn a
judgment that something works, but it cannot create authorization.

**Exceptions.** Each exception records the rule ID, the user's exact words or a verifiable source, the task/dataset/run,
the axes allowed to change, the time and the expiry conditions. A note that OOD was allowed, or a file name containing
ood, is not enough. Provider choice, GPU count, paid quota and data target are separate dimensions.

**Mode and references.** If the mode is unclear, ask first. Both OOD and non-OOD use real-world images and reach
real-world style. When real references are unavailable, pause rendering and state what is missing; do not switch to
text-only or structure-image generation. Reference leakage is a quality problem to fix and gives no permission to drop
the real references.

**Granted work.** Do not ask again for work the user already authorized, including GPU use, paid-provider calls and
recovery within the granted scope. Anything beyond the scope, or any other service, needs its own authorization. Asking
about the mode obtains goal information; it does not re-approve compute already granted. GPU and paid-provider
authorization comes from the current deployment and session; obtaining the repository grants none.

**One source of rules.** Long-lived behavior rules live in this repository. External AGENTS files and skills may only
link to the canonical version or distribute copies of the same version; they must not keep a semantically independent
set of rules.

**Technical decisions.** The orchestrating agent generates and measures the technical choices of a task, including the
adapter, judge, scene, brief and prompt. Do not turn these outputs into a to-do for the user. A flag-for-human from the
expert author goes to the orchestrator first; the name does not mean every technical failure interrupts the user.

# Data mode and real-world style

Video integrity and action alignment do not show that the data is what the user wants. Table-height randomization is a
simulation geometry design and cannot by itself authorize changing the table texture, the wall or the lighting. The
rendering service's model does not choose the data mode.

## The mode must be explicit

- `sim2real` means non-OOD: restore the appearance of this task's real target scene.
- `ood` means a change, relative to the recorded real baseline, that the user explicitly approved.
- `unresolved` is a state awaiting a question; submitting a render is forbidden.

If the user's current or standing instruction makes the mode of this task explicit, record the exact words and scope and
continue. Otherwise ask: "Should this batch be non-OOD (match the real scene) or OOD (please state the scope of change
explicitly)? Both will reference real images and keep real-world style." While waiting, continue observing, scene and
expert coding, and authorized small-sample validation that does not depend on the mode. Do not pick a mode and run it first.

An OOD run records the baseline, the axes of change, the value ranges, and the identities and relations that stay unchanged.
Allowing a change of table material does not allow a change of arm colour, object count or camera layout. An approved
axis allows only physically plausible changes that still look like real footage starting from the real baseline, not an
appearance detached from the real episode. Lighting diversity and hard shadows are not defects in themselves, but style
axes that were not approved must not be added. The absence of a general lighting constraint does not extend this task's scope.

## The inputs have different roles

- The white-mesh video provides the action, camera, timing, object presence, contact and terminal-state relations.
- The real images provide the whole-scene appearance baseline: the robot body, the attached cameras/cables and task
  objects that actually exist, the table/background, real materials and shapes, and the photographic feel of every view
  the task declares (all three for a head/left-wrist/right-wrist episode). A reasonable shape correction of a real object
  relative to its simulation proxy is not an action error.
- Pasting one wrist texture onto a scene that still looks like a white mesh does not count as adopting the real reference.
- A reference image has appearance authority only. It provides no object positions, action progress or camera layout.
  Never copy the action or layout from a reference, copy its arm or gripper into an empty area, or add entities absent from the source.

Each real reference has a source type, an acquisition note, a file hash, readability and a role. The white-mesh first
frame, generated images and continuity frames may be added but cannot pass for real images. A real-source claim needs an
auditable provenance record; a hash only proves the content is unchanged, not that the photo comes from the real world.

## Submission and review

Before submission, freeze the mode, the confirmation basis, the reference mapping, the prompt version and the provider.
The actual request must carry at least one valid real reference consistent with the frozen mapping; a path in a local
config does not count. Save credential-free submission metadata, the mapping from asset hashes to provider resource
identifiers, the final prompt and the request hash. Never save URLs with signed credentials.

After submission, review separately:

1. whether the real references were really submitted with the request;
2. whether the final video adopts the real appearance and has real-world style;
3. whether the action, topology and timing are preserved.

Both the executing agent and the independent reviewer personally open or decode the real image or episode frames and the
generated video, and compare them side by side. The prompt, hashes, the producer's summary or an earlier VLM text cannot
replace looking. Write `unverified` for any item lacking evidence, and do not borrow a pass from another item. Keep the
reviewer, frame ranges, evidence and judge version. A static three-frame preview is only a first screen and cannot show
that the timing of the whole video is normal.

The style check covers at least the real baseline, the material and shape of the arm body, the attached cameras/cables
and task objects that actually exist, the table/background, the photographic consistency of all declared views, and
reference-layout leakage. A component that does not exist is `not_applicable` with evidence and a reason, and must not be
invented. Every style pass saves a comparison image bound to the real reference and the generated video, the view and the
generated frame numbers. Whole-scene items use full-view evidence; a local texture or crop cannot claim full-scene
coverage. Judge against the real reference and the approved OOD changes: a reasonable real size, hard shadow or directional
light that deviates from the white mesh is not a defect. The default exposure threshold of 60/255 is a coarse guard and
cannot declare "real enough".

## No automatic downgrade

A missing mode, an OOD beyond authorization, a missing, unreadable or not-uploaded real reference, a source-only switch, a
reference replaced by a white-mesh frame, or an unverified review must never let production continue silently. Diagnostics
cannot waive the real reference either. If the user explicitly changes this requirement, first update the specification,
configuration, prompts and verification, and only then run.

Never backfill authorization into existing data: it keeps its evidence, a missing contract is unknown or needs-review, and
a re-check or re-capture produces a new version and certificate.

# Task cost

All model costs of a new task, from the real input to the white-mesh data, share one persistent ledger. The default mode
is advisory, with a target of 30 USD and a reference limit of 50 USD, configurable before prepare. It covers orchestration,
scene and interface implementation, expert development, independent review, failure retries and repairs. Photographic
generation and GPU compute are recorded separately and are outside this model budget. The price basis, model/tier, caching
and unknown usage must be traceable. The target is not a promise that every new task can succeed within that amount.

The user's request governs. Never change the task definition, data count, mode or success criteria silently to save money.
A count that was not explicit is an execution assumption and must not be written as a user request. The quality and
independent-review requirements stay in force.

## How to work

- One main executor drives progress. The parent chat receives stage results; run no second scheduler and no per-minute
  model polling. Use programs for scheduling, log polling, counting and hash comparison. `pipeline_agent.py wait` waits for
  a substantive change of task state. Give progress updates the user asked for, but do not open a model subtask just to
  produce the same status.
- Load only the skills the current stage needs; do not inject all rendering, training, development and review rules every
  round. A stage handoff passes the input/code/contract hashes, a result summary, the main failures, output paths, the
  remaining budget and in-flight IDs. Raw logs stay in the outputs and are viewed on demand.
- Reuse the verified general robot interface, collection, clock, image encoding and statistics tools. The semantics,
  adapter, expert and judge of a new task are still generated from current evidence; reusing tools never copies another
  task's authorization or skips this task's verification.
- First confirm with 2-3 discriminating samples that the necessary physical actions are feasible, and only then start
  expert trial and error. Repair the largest failure group first. Do not let the expert burn budget on a low-level action
  interface known to fail.
- Deterministic checks with the same source, contract, judge and environment hashes can be reused. When something changes,
  redo only the affected checks, then the required final independent acceptance. The visual review of an earlier sample
  cannot replace the review of a new video.
- Label general infrastructure work and routine task runs separately. Infrastructure spending incurred for a task still
  counts toward that task's end-to-end total; changing the category does not remove it. Opening separate infrastructure
  work is a new scope and does not enlarge the budget.

## Modes

`prepare` pins `configs/task-cost-policy.json` and saves the policy hash and a persistent ledger.

- `disabled`: no threshold scheduling, but all sessions, known costs and unknown liabilities are still saved.
- `advisory` (default): hints from target and limit. `on_excess=warn` continues; `pause` pauses once the known cost reaches
  the limit. Unknown costs are marked, and you must not claim the total is within budget.
- `enforced`: needs a metered driver that can limit itself and all its child calls. Reservations, unsettled amounts, unknown
  receipts and overruns block continuation. A post-hoc token estimate cannot replace a hard limit.

Native Codex uses the existing login and saves JSONL token usage. Without a reliable dollar receipt, `cost_usd=null` and the
total cost is unknown. The native CLI does not satisfy enforced, and declaring `cost_control` does not make it so. Missing
usage is never zero, and the known cost is only a subtotal. `disabled` does not delete costs or cancel the physical, video,
independent-review and provenance contracts. Record an overrun as it is.

Never rewrite the policy or its hash, delete the ledger, or create a new task to remove earlier costs. Adjust the quota of a
new task before prepare. A configuration change during a run keeps the control history and does not reset the task policy,
the session count or the retry state. When model consumption outside the driver is not covered, mark the end-to-end cost as
incompletely covered. A claim of cost savings needs a measurement on the same task with the same data volume, difficulty and
judge; software tests only show budget and state behaviour.

## Waiting without a model

`pipeline_agent.py wait` only polls `state.json`. It calls no model and changes no task state. It returns when
phase/status/next_action/questions or the ID/status/error of `external_jobs` changes, not on a heartbeat. `complete` is only
a status notification; the delivery must still be verified.

When the only next step is waiting for a submitted job, write `"model_wait_for": ["job-id"]` in `state.json` and save the same
ID and the real status in `external_jobs`. Before creating a session, `drive` checks these dependencies and returns
`waiting-external-jobs` until they end. The external supervisor keeps monitoring the real process and updating the status. A
heartbeat, an unknown status or an observation timeout must not be written as a failure followed by a duplicate submission.
When independent work remains, do not set this field; clear it after the dependencies are handled.

Protocol details: `docs/reference/cost-control.md`.


--- PROJECT INSTRUCTION: prompts/roles/scene-author.md ---
You author one scene layout (`datafarm.scene-layout/1`) for the data request the host gives you. You are the producer, not the judge: the host runs the deterministic gates after every session and decides acceptance. Your own statement that the layout is correct counts for nothing; only the host diagnostics do.

Job: write `scene-layout.json` in your working directory (the workspace) so that it faithfully implements the request in `request.yaml` and passes the host gates. Each session ends when you stop; the host then reads only that file. If the previous round failed, the prompt lists the host diagnostics one per line: fix every line, keep what already passed, and do not rewrite unrelated parts.

Format: `docs/ir/scene-layout.md` is the authority for every field, unit and default; read it in full. Its excerpt shows the shape of a document only. Layouts written for other requests or tasks, including files under `examples/scene/` and any `runs/` output, are outputs of other tasks: do not read, copy or adapt them. Derive every value from this request, the assets you choose and the host evidence.

Tools you may use:
- `python tools/simready.py --endpoint <endpoint> search <terms> [--require-joint prismatic|revolute] [--probe]` and `... probe <asset>`; the prompt gives the exact command with the configured endpoint. Probe output names joints (with axis and limits when authored), license and source collection. Choose assets whose license and joints fit the request; `assets[].simready` is the SimReady directory name.
- Read-only host evidence in `host/` inside the workspace, written after each round: `asset-records.json` (AssetRecords of the asset set the host last prepared: bounding boxes, collision boxes, joint names and limits, robot base collision box), `plan.json` (resolved poses, footprint, reachability with per-target position error) and `last-attempt.json` (the last host verdict). Absent files mean the host has not produced them yet.
- Do not fetch assets, run `tools/scene_assemble.py`, start a simulator or GPU job, or edit files outside the workspace. The host fetches and prepares the asset set you declare, only when that set changes; use joint names and dimensions from `host/asset-records.json` once it exists, not guesses.

Rules the gates enforce (rule values live in `configs/scene-roles.json`):
- Node ids: a request object with `count: 1` maps to exactly one node whose `node_id` equals its `object_id`; with `count: N` use `<object_id>.0` ... `<object_id>.<N-1>`. No other nodes except the robot node.
- Roles: the layout asset used by a node has the request object's `role`. A receptacle asset needs a joint of the requested type.
- Support: each node's `on` equals the request `constraints.support` (default `floor`).
- Joint state: `joint_state: open` means at least one joint of the requested type sits at or above the open fraction of its range (measured from the lower limit); `closed` means at or below the closed fraction. Values must stay inside the AssetRecord limits.
- Robot: `robot.package_asset` (and `asset_id` when the rules name one) must match the request robot; pick `tcp_link`, `tcp_frame_id` and `tool_approach_axis` that the robot model provides.
- Reach targets: every task object and receptacle needs reach targets on its own node. Cover the grasp region of the task object and the release region where it must end up (for a drawer, targets that use the drawer `joint` so they move with the opening); reachability is checked from above by default.
- Probes: a receptacle needs a probe on its node whose asset is a task-object asset, with a rest-height interval consistent with the receptacle geometry.
- Randomization: task objects declare `randomization` (`position_jitter_m` and/or `yaw_range_deg`).
- `collision_groups` names only declared node ids (robot node included); `contact_with` and `forbidden_with` never overlap.
- Footprint: objects on a support stay inside its top and do not overlap each other or the robot base.

What the host checks before acceptance: request conformance with AssetRecords (complete, nothing skipped) and the plan (footprint and kinematic reachability). The Isaac Lab `check` (settle, penetration, probes) runs later on a GPU host, so keep probe intervals and clearances physically honest rather than tuned to pass. Report in your final message what you chose and why, separating what the host evidence showed from what you assumed.

# Request — `datafarm.request/1`

数据请求：用户要什么数据。1a 把一句自然语言经一次结构化 LLM 调用写成 `request.yaml`，1b 的 coding agent 据此写 `datafarm.scene-layout/1`，后续阶段从这里读 episode 数、seed 分区、相机和渲染变体。

A 线普通文档（不套 kernel 信封），YAML 或 JSON 均可。它**只写意图**：不带坐标、位姿、资产 ID（SimReady 名、USD 路径）或主机路径；这些由 1b 检索、组装后写进 scene-layout / SceneGraph。校验器是 `src/datafarm/request/schema.py::validate_request`，1a 的结构化输出 schema 由 `request_json_schema()` 从同一个模型导出。

## 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `schema` | 是 | 固定 `datafarm.request/1` |
| `request_id` | 是 | 标识（见 [README §4](README.md#4-标识)），如 `plate-drawer-airbot-001` |
| `robot` | 是 | 机器人能力表 `ROBOT_CAMERAS` 里的键；目前只有 `airbot_single_g2`（单臂，左臂 + G2 夹爪） |
| `task` | 是 | 一句自然语言目标，如 `put the plate into the open drawer`；判定器与专家由后续阶段从它派生 |
| `scene` | 是 | 场景意图，见下 |
| `episodes` | 是 | 要交付的合格 episode 数，正整数 |
| `seeds` | 是 | `{dev: [first, last], holdout: [first, last]}`，见下 |
| `cameras` | 是 | 要记录的机器人相机 id，不重复，必须是该机器人装了的相机，见下 |
| `render` | 是 | `{engine, views, materials, lights}`，见下 |
| `dataset` | 是 | `{format: "hdf5"}`；目前只有 HDF5 |

`scene`：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `setting` | 否 | 场景类型，snake_case，如 `kitchen` |
| `objects` | 是 | 物体数组，至少一个 `role=task_object`，见下 |
| `asset_sources` | 否 | 允许的资产来源，按偏好排序：`simready` / `partnet_mobility` / `usdcraft` / `local`（同 AssetRecord `source.kind`）；省略表示不限 |

`scene.objects[i]`：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `object_id` | 是 | 请求内唯一的标识，如 `object.plate`；1b 写 scene-layout 时沿用为 `node_id`。`floor` 保留 |
| `category` | 是 | 物体类别，snake_case 名词，如 `drawer_cabinet`；1b 用它检索资产 |
| `role` | 是 | `task_object` / `receptacle` / `background`（AssetRecord `role` 去掉 `robot`、`camera_rig`） |
| `constraints` | 否 | 结构化约束，见下；省略等于 `{}` |
| `count` | 否 | 相同实例个数，默认 1 |

`constraints`（字段都可选，不接受其他键，不接受自由文本）：

| 字段 | 说明 |
| --- | --- |
| `joint` | 物体必须具有的关节：`prismatic` / `revolute`（抽屉滑轨是 `prismatic`） |
| `joint_state` | 该关节初值：`open` / `closed`；必须同时给 `joint` |
| `shape` | 形状特征，snake_case，如 `raised_rim` |
| `support` | 放在哪个物体上：另一个 `object_id` 或 `floor`；对应 scene-layout 节点的 `on` |

`render`：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `engine` | 是 | 固定 `"isaac_rtx"`，同 [RenderSpec](render-spec.md) |
| `views` | 是 | 视角 id 数组，不重复：机器人相机 id（必须也在 `cameras` 里）或虚拟视角名（如 `third_person`）；位姿由 RenderSpec 决定 |
| `materials` | 是 | 每个视角的材质变体数，≥1；1 表示保持资产原材质 |
| `lights` | 是 | 每个视角的光照变体数，≥1；1 表示保持场景原光照 |

变体总数 = `len(views) × materials × lights`，由 RenderSpec 展开成具体 `variants`。

## 约束

- **seed 分区**：`dev` 与 `holdout` 都是闭区间 `[first, last]`，`0 ≤ first ≤ last`，两区间不得相交（`[0, 99]` 与 `[100, 119]` 合法，`[0, 99]` 与 `[99, 120]` 不合法）。`dev` 给专家作者调试，`holdout` 只给冻结判定器验收；`holdout` 不得出现在作者能看到的任何上下文里。
- **相机能力**：`cameras` 必须是 `ROBOT_CAMERAS[robot]` 的子集。`airbot_single_g2` 只有 `head` 与 `left_wrist`，**没有 `right_wrist`**；请求双腕会被拒绝，而不是静默丢掉。能力表只在 `schema.py` 一处维护。
- **支撑关系**：`support` 引用的 `object_id` 必须存在，支撑链无环且最终落在 `floor` 或无 `support` 的物体上。
- `object_id` 唯一；至少一个 `task_object`。
- 类型严格：`episodes: "20"`、`materials: 2.0` 一律拒绝，不做隐式转换；未知字段一律拒绝。
- 复用 kernel 的可移植性检查（`canonical_json_bytes`）：不得出现绝对路径、`*_path` / `*_file` 字段、凭据字段或带 query 的 URL。
- JSON Schema 只覆盖结构；seed 不相交、引用存在、相机能力这类跨字段约束只在 `validate_request` 里检查。1a 拿到 LLM 输出后必须再过一遍 `validate_request`。

# SceneLayout — `datafarm.scene-layout/1`

场景布局说明：A 线普通文档，是 `tools/scene_assemble.py` 的输入。它只描述"放什么、放在哪、要够到哪"，
不描述资产本身的几何、碰撞和物理量；那些来自 SimReady 资产与 [AssetRecord](asset-record.md)。
`prepare` 读 `assets[]` 生成本地资产记录，`plan` 读其余节解位姿并做静态检查，`check` 再读 `probes[]`
和 `collision_groups` 在仿真里验证，最后产出 [SceneGraph](scene-graph.md)。

字段先少而准：布局只写水平位置、偏航角、支撑面和关节初值，高度由支撑面顶面与资产包围盒底面算出，
避免手填 z 造成悬空或穿模。改布局时在 `plan` 这一步迭代，不必启动仿真器。

## 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `schema` | 是 | 固定 `datafarm.scene-layout/1`；`resolve_nodes` 第一行校验 |
| `scene_id` | 是 | 如 `scene.plate_drawer_airbot`；`check` 写 SceneGraph 时用，必须符合 IR 标识符规则 |
| `assets` | 是 | 要检索并预处理的资产数组，见下；`prepare` 按此逐项处理 |
| `nodes` | 是 | 场景实例数组，见下；顺序即 `plan.json` 里 `nodes` 的顺序 |
| `robot` | 是 | 机器人挂载、TCP 与可达性参数，见下 |
| `reach_targets` | 是 | 可达性目标数组，见下；可以为空数组（此时可达性 trivially ok） |
| `probes` | 否 | 放置探针数组，仅 `check` 使用；缺省为空 |
| `collision_groups` | 是 | 接触判定分组，原样写进 SceneGraph；`check` 时校验，见下 |
| `cameras` | 否 | 相机数组，原样写进 SceneGraph 的 `cameras`；缺省为空 |

### `assets[i]`

对应一个 SimReady 资产或手动放置的资产。`prepare` 用 `--cache/<simready>/` 定位资产目录，
目录里必须有 `simready-fetch.json`；处理后 `asset_id` 成为 AssetRecord 的主键，也是 `nodes[].asset_id`
和 `robot.asset_id` 的取值来源。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `asset_id` | 是 | 资产标识，如 `object.plate`；同一文档内唯一 |
| `role` | 是 | `robot` / `task_object` / `receptacle` / `background` / `camera_rig`，写进 AssetRecord；`receptacle` 必须有 prismatic/revolute 关节 |
| `simready` | 是 | `--cache` 下的目录名，如 `dishware_plastic_bigPlate_a01`；目录里必须有 `simready-fetch.json`。机器人不写进 `assets[]`，由 `robot.package_asset` 单独处理 |
| `body` | 是 | `kinematic` / `rigid` / `articulation`，决定 Isaac Lab 用 `RigidObjectCfg`（kinematic 时 `kinematic_enabled=true`）还是 `ArticulationCfg` |
| `anchor_body` | `body=articulation` 时是 | 基座刚体在包装层里的 prim 路径（`prim_ref` 形式）；`prepare` 给它加固定关节锚到资产根 Xform |

`assets[]` 里不写 USD 路径、俯仰/翻滚角或物理参数：姿态只有偏航，高度由布局解出，
质量/摩擦/阻尼写在 AssetRecord 的 `physical_quantities` 里。

### `nodes[i]`

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `node_id` | 是 | 场景内唯一标识，如 `object.plate`；同时作为 Isaac Lab prim 名和 SceneGraph node id |
| `asset_id` | 是 | 必须出现在 `assets[]`，且 `prepare` 已为它产出 AssetRecord |
| `semantic_tag` | 是 | `table` / `drawer` / `plate` / `background` / `robot`；判定器和渲染按此查找 |
| `xy_m` | 是 | 世界系水平位置 `[x, y]`，m；高度不在这里给 |
| `yaw_deg` | 否 | 绕世界 +Z 的偏航角，度，默认 0；四元数固定 xyzw |
| `on` | 否 | 支撑节点 id 或 `"floor"`，默认 `"floor"`；决定 z 和占地检查的支撑面 |
| `z_m` | 否 | 显式覆盖解算出的高度，m；给了就不再按支撑面算，但仍按 `on` 决定子节点顶面和占地归属 |
| `joint_state` | 否 | `{关节名: 初值}`；关节名是上游 USD 里的名字（AssetRecord `joints[].name`），值必须在该关节 `limits` 内 |
| `randomization` | 否 | `{position_jitter_m, yaw_range_deg}`，原样写进 SceneGraph；`yaw_range_deg` 是度且在 `[-180, 180]` |

高度解算规则（`layout.resolve_nodes`）：

- `on="floor"`：基准面 `z=0`；否则先递归解出支撑节点，基准面取它的顶面。
- 支撑包围盒优先取 AssetRecord 的 `collision.bbox_*`（碰撞凸包，物理接触发生在那里），没有则取 `frames.bbox_*`，
  再没有才用 `bbox_m`。顶面高度 = 支撑节点 z + 该包围盒 `max_z`。
- 节点 z = 基准面 + `SUPPORT_CLEARANCE_M`（0.001 m）− 自身包围盒 `min_z`，结果取 6 位小数。
- 支撑依赖必须无环、指向已知节点；未知资产、未知节点、关节值越界都是 `IRError`。
- 同一 `node_id` 在 `nodes[]` 里重复出现时后者覆盖前者，不单独报错，作者要自己保证唯一。

### `robot`

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `node_id` | 是 | 机器人在场景内的 node id，如 `robot.airbot`；写进 SceneGraph |
| `asset_id` | 是 | 机器人 AssetRecord 的 id，`prepare` 用 `package_asset` 生成它 |
| `package_asset` | 是 | 机器人包 `delivery_manifest.json` 里的资产名（如 `airbot_single`）；`plan`/`check` 用它重新解析 URDF |
| `on` | 无 `base_pose` 时是 | 支撑节点 id 或 `"floor"` |
| `xy_m` | 无 `base_pose` 时是 | 世界系水平位置 `[x, y]`，m |
| `yaw_deg` | 否 | 偏航角，度，默认 0 |
| `base_pose` | 否 | 显式基座位姿；给了就原样使用，忽略 `on`/`xy_m`/`yaw_deg` |
| `arms` | 是 | 数组，MVP 写 `["left"]`，允许 `left`/`right` 的非空子集 |
| `gripper` | 是 | 固定 `"g2"` |
| `tcp_link` | 是 | 模型 TCP 所在 link；`robot-descriptor` 的 `model_semantics.tcp_candidates` 必须有该 link 的候选，否则报错 |
| `tcp_frame_id` | 是 | TCP 坐标系名，如 `tcp.left`；写进 SceneGraph `frames` |
| `tool_approach_axis` | 是 | 工具系里指向接近方向的轴，`x` / `y` / `z` |
| `limit_margin_rad` | 否 | IK 关节限位余量，rad，默认 0.05 |

无 `base_pose` 时，基座高度让基座刚体碰撞体底面贴在支撑顶面：`z = 支撑顶面 + SUPPORT_CLEARANCE_M − collision.base_bbox_min_m[2]`。
AssetRecord 没有 `collision.base_bbox_min_m` 时报错，不假设基座原点就是底面。

### `reach_targets[i]`

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `name` | 是 | 目标名，出现在 `plan.json` 的行和 diagnostics 里 |
| `node` | 是 | 目标写在其局部系的节点 id |
| `local_m` | 是 | 节点局部系下的位置 `[x, y, z]`，m |
| `joint` | 否 | 棱柱关节名；目标随该关节初值沿关节轴平移（抽屉内腔）。只接受 prismatic，其他类型报错 |
| `approach` | 否 | 世界系接近方向，代码会归一化；默认 `[0, 0, -1]`（自上而下） |
| `yaw_samples` | 否 | 绕接近轴尝试的转角数，默认 8；任一转角求得逆解即判可达 |

目标世界坐标 = 节点位姿 ×（`local_m` + 关节轴 × `joint_state[joint]`，缺省 0）。`joint` 写的是关节初值平移量，
不是当前测量值。

可达性用多起点阻尼最小二乘 IK，作用在 `tcp_link` 的模型 TCP 上，关节夹在 `[lower+margin, upper−margin]`；
不做碰撞感知规划，也不检查抓取姿态。"没解出来"只说明这些起点下局部未收敛，不能证明全局不可达。

### `probes[i]`（仅 `check`）

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `name` | 是 | 探针名，写进 `check.json` 的 evidence |
| `asset_id` | 是 | 被传送、自由落下的资产；取 `nodes[]` 里第一个使用该资产的节点 |
| `node` | 是 | 目标局部系节点，同时作为期望接触的支撑节点 |
| `local_m` | 是 | `node` 局部系下的投放位置，m |
| `joint` | 否 | 同 `reach_targets[].joint`，投放点随棱柱关节初值平移 |
| `expect_rest_z_min_m` / `expect_rest_z_max_m` | 是 | 静止高度的接受区间，m（世界系） |

探针把物体传送到目标点，自由落体若干秒后检查：末速度低于阈值、静止高度在区间内、与 `node` 有接触。
用来证明"抽屉内腔装得下盘子且能托住"。

### `collision_groups`

`{group_id: {entities: [...], contact_with: [...], forbidden_with: [...]}}`，原样写进 SceneGraph。
`check` 时（`scene_graph.validate`）校验：三个列表都必须是已声明的 node id，`contact_with` 与
`forbidden_with` 不能有交集。`entities` 是本组主体，`contact_with` 是允许接触的对象，
`forbidden_with` 是违规接触的对象；判定器据此区分允许接触与违规接触。

### `cameras`

可选数组，原样进入 SceneGraph 的 `cameras`，由 `scene_graph.validate` 校验。每个相机的字段
（`camera_id`、`kind`、`mount`、`offset`、`intrinsics`、`optical_frame`、`distortion`、`fps`）见
[scene-graph.md](scene-graph.md)；`fps` 必须整除 120。布局本身不读相机。

## 单位与坐标系

- 长度 m，角度：`yaw_deg` / `yaw_range_deg` 用度，`limit_margin_rad` / `yaw_rad` 用弧度。
- 右手系、Z 向上；节点位姿是 `frame_id="world"` 的 `T_world_node`。
- 偏航四元数固定 xyzw：`[0, 0, sin(yaw/2), cos(yaw/2)]`，只绕 +Z。
- 支撑包围盒来自资产根系；碰撞凸包会比渲染网格外扩几毫米，布局按碰撞包围盒算支撑高度。

## `plan` 与 `check` 各验证什么

`plan`（纯 Python + numpy，不启动仿真器）：

1. 解出全部节点位姿，检查 schema、支撑无环、资产存在、关节初值在限位内。
2. 机器人基座位姿（显式 `base_pose` 或按基座碰撞体底面贴支撑面）。
3. 占地检查：每个非 floor 节点（以及由 `on`/`xy_m` 解出的机器人基座）的包围盒底面矩形按偏航旋转后，
   必须落在支撑节点顶面包围盒内；同一支撑面上的物体（floor 也算同一支撑面）两两不许相交。
   机器人给了显式 `base_pose` 时不参与占地检查。只适用于平放物体。
4. 逐个 `reach_targets` 求逆解，全部有解才 ok。
5. 写 `plan.json`：`spec_sha256`、`nodes`、`robot_base_pose`、`reachability`、`footprint`，外加 `ok`
   （可达性与占地的合取）。退出码 0 当且仅当 `ok=true`。

`check`（Isaac Lab 3.0 + Newton/MJWarp）：

1. 读 `plan.json`，`spec_sha256` 与当前布局不一致直接报错，要求重跑 `plan`。
2. 加载场景，显式写入 `joint_state` 并读回校验（`scene.reset()` 不会把它写回仿真）。
3. 静置检查漂移/末速度/关节漂移，接触缓冲检查穿透，跑 `probes`。
4. 用 `plan` 的 `nodes`、`robot_base_pose`、`reachability` 拼 SceneGraph 并过校验。
5. 退出码 0 当且仅当静置稳定、无穿透、探针全过、可达性 ok、占地 ok。`plan.json` 的 `ok` 不参与判断，
   `check` 分别读 `reachability.ok` 与 `footprint.ok`。

## 请求符合性

`datafarm.scene.conformance.check_conformance(request, layout, records, rules)` 在 `plan` 之前做确定性检查，
确认布局忠实实现了 [Request](request.md)。它不碰几何和物理，只比对结构；能否摆下、够到仍由 `plan`/`check` 决定。

```python
report = check_conformance(request, layout, records, rules)  # rules = load_role_rules("configs/scene-roles.json")
report.ok        # 没有 problems
report.problems  # list[str]，一行一条
report.skipped   # 因缺 AssetRecord 而跳过的关节检查
report.complete  # 没有 skipped
```

- **节点映射**：`count=1` 时 `node_id == object_id`；`count>1` 时用 `<object_id>.<i>`（i 从 0 起）。
  每个请求物体恰好对应一个布局节点，布局里不允许请求之外的节点（机器人节点除外）。
- **角色**：布局 `assets[].role` 必须等于请求 `role`。
- **支撑**：`constraints.support`（缺省 `floor`）必须等于节点 `on`（缺省 `floor`）。
- **关节**：请求给了 `joint` 时，AssetRecord 必须有该类型的关节；`joint_state: open` / `closed`
  把关节位置按行程 `[lower, upper]` 从下限归一化，`open` 要求至少一个该类型关节 ≥ `open_min_fraction`，
  `closed` 要求至少一个 ≤ `closed_max_fraction`。没有传 AssetRecord 时这些检查记为 `skipped`，
  `complete=False`；`ok` 仍可能为真，调用方自己决定是否接受不完整报告。
- **机器人**：布局 `robot.package_asset`（规则表给出 `asset_id` 时也检查它）必须匹配请求 `robot`。
- **资产来源**：请求给了 `scene.asset_sources`、布局资产又带 `simready` 时，`simready` 必须在允许列表里。
- **角色规则**：见下表，取值在 `configs/scene-roles.json`。

| 角色 | 规则 |
| --- | --- |
| `task_object` | 至少 1 个 `reach_targets` 指向该节点；节点必须声明 `randomization`（`position_jitter_m` 或 `yaw_range_deg`） |
| `receptacle` | 至少 1 个 `reach_targets` 指向该节点；至少 1 个 `probes` 的 `node` 是该节点，且该 probe 的资产属于某个 `task_object` 节点 |
| `background` | 无额外规则（`reach_targets_min: 0`） |

规则表 schema 为 `datafarm.scene-roles/1`：`roles.<role>.reach_targets_min` / `require_probe` /
`probe_asset_role` / `require_randomization`，`joint_state.open_min_fraction` / `closed_max_fraction`，
`robots.<request robot>.package_asset`（可选 `asset_id`）。阈值都按关节行程从下限起算。

## 限制

- 节点只有偏航，不支持俯仰/翻滚；占地检查假设物体平放。
- 布局不检查手臂与柜体/桌子的碰撞，也不检查抓取姿态；这些留给 B 线规划和判定。
- 可达性只算运动学；"没找到解"不是全局不可达的证明。
- 布局不写资产物理参数，质量、摩擦、恢复系数、抽屉阻尼来自 AssetRecord，标为 `assumed`。
